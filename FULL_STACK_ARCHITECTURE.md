# Full-Stack Web Architecture Documentation

This document is the single source of truth for how the WOMAN system is organized across frontend, backend, database, and deployment infrastructure.

## 1. Executive Architecture Overview

The application follows a decoupled client-server architecture:

1. Users access a static multi-page frontend (role-based pages for admin, client, technician/head).
2. Frontend JavaScript calls backend REST endpoints over HTTP using `fetch`.
3. Backend (Node.js + Express) validates auth and role permissions, runs business logic, and reads/writes MySQL data.
4. Backend returns JSON responses consumed by frontend scripts.
5. Ticket attachment files are uploaded via `multer` and served from `/uploads`.

Current codebase behavior:

- API base path: `/api/*`
- Health endpoint: `/api/health`
- JWT auth: `Authorization: Bearer <token>`
- Session persistence: browser `localStorage`/`sessionStorage`

## 2. Frontend (Client-Side) Architecture

### 2.1 Technology Stack

- Rendering model: Static HTML pages with vanilla JavaScript modules
- Styling: Custom CSS in `frontend/styles/global.css`
- Web server in container: Nginx (Alpine image)
- Routing model: File/path-based pages by role (`/admin`, `/client`, `/technician`)

### 2.2 Frontend Responsibilities

- Login/session bootstrap and token persistence
- Role guards and role-based navigation rendering
- API request orchestration and response handling
- Ticket CRUD, messaging, profile management, admin operations
- File attachment upload via `FormData`

### 2.3 Frontend Runtime Config

Defined in `frontend/js/config.js`:

- Local default API: `http://localhost:5000/api`
- Deployed fallback API: Railway URL
- Supports runtime override through `window.APP_CONFIG.API_BASE_URL`

## 4. Backend (Server-Side) Architecture

### 4.1 Technology Stack

- Runtime: Node.js (Dockerfile uses `node:18-slim`)
- Framework: Express 4
- Module system: CommonJS
- Auth: JWT (`jsonwebtoken`)
- Password hashing: `bcrypt` / `bcryptjs`
- File uploads: `multer`
- Email integration: `nodemailer`

### 4.2 Layered Design Used in This Project

1. Route Layer (`backend/routes/*.routes.js`)
- Maps URL paths to handler functions and middleware chain.

2. Service Layer (`backend/services/*.service.js`)
- Holds business logic and DB interactions for each domain.

3. Data Access
- Uses `mysql2/promise` pool from `backend/config/db.js`.
- Queries are currently SQL-based (no ORM).

### 4.3 AuthN/AuthZ

- `authenticate` middleware validates bearer token and refreshes user status from DB on each request.
- `authorize(...roles)` middleware enforces RBAC.
- Disabled accounts are immediately blocked with `403`.

### 4.4 Core Route Groups

- `/api/auth`
- `/api/tickets`
- `/api/users`
- `/api/companies`
- `/api/departments`
- `/api/logs`
- `/api/profile`
- `/api/messages`
- `/api/password-recovery` (mounted through `/api` path group)
- `/api/admin`

## 5. Data Layer (Database and Files)

### 5.1 Primary Database

- Engine: MySQL 8.0
- Driver: `mysql2` pool
- Default local container mapping: host `3307` -> container `3306`

### 5.2 Schema and Migration Strategy

- Base schema bootstrap: `backend/database.sql` (mounted into MySQL init directory in Compose)
- Incremental changes: `backend/migrations/*.sql`
- Auto-apply on backend startup via `applyMigrations()` in `server.js`
- Manual run option: `node backend/scripts/run_migrations.js`

### 5.3 Seed Data

- Seed script: `backend/scripts/seed.js`
- Seeds users, companies, departments, tickets, responses, and logs.

### 5.4 File Storage

- Upload path: `backend/uploads/ticket_responses`
- Served statically via `/uploads`
- Persistent Docker volume for backend storage: `backend_storage`

## 6. Infrastructure, DevOps, and Deployment

### 6.1 Local Environment (Docker Compose)

Services in `Docker-compose.yml`:

1. `backend`
- Built from `backend/Dockerfile`
- Exposes `5000`
- Depends on `db`

2. `frontend`
- Built from `frontend/Dockerfile`
- Exposes `3001` externally -> `80` in container
- Nginx proxies `/api` to backend service

3. `db`
- `mysql:8.0`
- Exposes `3307` locally
- Persists data via `db_data` volume

### 6.2 Cloud Deployment

- `render.yaml` is configured for a Docker web service currently targeting the backend Dockerfile.
- Includes environment variables for DB and JWT settings.

Note: frontend config currently includes a Railway backend fallback URL in `frontend/js/config.js`.

## 7. Security Architecture (Current + Recommendations)

### 7.1 Implemented

- CORS middleware with allowlist support through `ALLOWED_ORIGIN`
- JWT-based authentication
- Role-based authorization middleware
- Password hashing with bcrypt
- Environment variable based configuration (`.env`)

### 7.2 Gaps and Hardening Opportunities

- Secrets are present as plain values in `render.yaml`; move to managed secret storage.
- Local storage token strategy is vulnerable to XSS exfiltration risk; consider httpOnly cookie strategy.
- No dedicated rate-limiting middleware found; add request throttling for auth-sensitive routes.
- Add `helmet` and explicit input validation layer (e.g., Joi/Zod) across all write endpoints.

## 8. API Design Contract

### 8.1 Base URL Pattern

- Local dev via frontend config: `http://localhost:5000/api`
- Containerized frontend proxy: `/api/*` routed to backend

### 8.2 Response Conventions (Observed)

- Success responses typically return:
  - `success: true`
  - domain payload (`user`, `users`, `ticket`, `tickets`, etc.)

- Common error statuses:
  - `400` validation/data issues
  - `401` missing/invalid/expired token
  - `403` unauthorized role or disabled account
  - `404` route/resource not found
  - `500` unexpected server error

### 8.3 Health Check

- `GET /api/health` returns service status, version, and timestamp.

## 9. Known Structural Notes

- There is a nested duplicate directory at `smis-woman/smis-woman/` with mirrored backend/frontend files.
- This can create maintenance drift if both trees are edited independently.
- Recommended: define one canonical source tree and archive/remove the duplicate after validation.

## 10. Suggested Next Improvements

1. Consolidate duplicate project tree (`smis-woman/smis-woman`) to prevent divergence.
2. Standardize one production API base URL strategy (avoid hardcoded fallback URLs in frontend code).
3. Add CI pipeline (lint/test/build) and enforce checks on pull requests.
4. Add centralized request validation and security middleware hardening.
5. Add formal API spec (OpenAPI/Swagger) for client-backend contract visibility.
